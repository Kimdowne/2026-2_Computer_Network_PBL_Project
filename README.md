# 2026-2_Computer_Network_PBL_Project

## 1. 프로젝트 개요

프로젝트명:
「소규모 사내망 설계 및 Wireshark 기반 통신 검증·장애 진단」

수행 과목:
컴퓨터네트워크PBL

수행 기간:
12주, 약 3개월

참여 인원:
총 4명, A·B·C·D

프로젝트의 중심 질문:
“웹 서비스에 접속되지 않거나 응답이 느릴 때, 통신이 어디까지 진행되었는지 확인하고, 설정과 패킷을 근거로 원인을 좁힌 뒤 정상화 여부를 검증할 수 있는가?”

가상의 소규모 회사 네트워크를 구성한다. 직원망과 서버망을 분리하고, 직원 클라이언트가 IP 주소를 할당받아 내부 웹 서버에 이름으로 접속하도록 만든다. 이후 통제된 설정 오류와 서비스 장애를 발생시키고, Wireshark와 기본 진단 도구로 분석·복구한다.

핵심 흐름은 다음과 같다.

네트워크 설계 → 설정 → 정상 통신 확인 → 장애 재현 → 패킷·설정 분석 → 최소 수정 → 복구 검증

처음부터 고급 보안관제 시스템이나 공격 도구를 개발하는 프로젝트가 아니다. 입문자가 통신 원리를 실제로 확인하고, 기초적인 네트워크 운영·장애 진단 역량을 획득하는 프로젝트다.

## 2. 참여자 수준과 역할

A:
- 기초적인 ICT 지식이 있다.
- 네트워크 전문가나 숙련된 서버 관리자는 아니다.
- 준비된 설명과 예제를 바탕으로 공용 서버와 가상 실습 환경 구성을 주도한다.
- A에게도 명령의 의미, 실행 위치, 정상 확인, 오류 해결 방법을 설명해야 한다.
- 환경 구성만 맡는 것이 아니라 모든 공통 실습과 개인 분석에 참여한다.

B·C·D:
- IP 주소의 의미부터 배워야 하는 네트워크 입문자다.
- Linux 명령, SSH, 가상 네트워크, Wireshark에도 익숙하지 않을 수 있다.
- 명령을 실행하는 위치와 결과를 확인하는 방법까지 안내가 필요하다.

역할 운영 원칙:
- 셋업은 A가 주도하지만 주소 계산, 클라이언트 설정, 경로 설정, 캡처 분석, 장애 진단은 네 명 모두 직접 수행한다.
- “셋업 담당자 활동”과 “실습 참여자 활동”을 분리한다.
- 실습 참여자는 A·B·C·D 전원이다.
- 한 명이 실행하고 세 명이 보기만 한 활동은 개인 실습 완료로 취급하지 않는다.
- 공유 서버에서 설정 변경은 차례대로 수행하고, 내려받은 캡처 분석은 동시에 수행할 수 있다.
- 팀 토의 전에 각자 관찰 사실과 판단 근거를 작성한다.
- 평가에서는 A도 정답을 모르는 사례를 분석한다. 다른 참여자가 준비된 조건 중 장애를 선택하고 정답을 보관한다.

## 3. 학습 목표

네 명 모두 프로젝트 종료 시 다음을 수행할 수 있어야 한다.

1. IP·MAC·포트의 역할을 구분한다.
2. 요구 장치 수를 보고 서브넷과 주소 범위를 정한다.
3. 같은 서브넷과 다른 서브넷으로의 통신 차이를 설명한다.
4. 기본 게이트웨이, 직접 연결 경로, 정적 경로, 반환 경로를 구분한다.
5. ARP·ICMP·DHCP·DNS·TCP·HTTP를 패킷에서 식별한다.
6. DNS 조회, TCP 연결, HTTP 요청·응답을 순서대로 설명한다.
7. HTTPS에서 일반 캡처로 확인할 수 있는 정보와 없는 정보를 구분한다.
8. 설정 오류와 서비스 장애의 원인 후보를 증거로 좁힌다.
9. 설정을 수정한 뒤 같은 조건으로 정상화를 검증한다.
10. 관찰 사실, 추정, 추가로 필요한 증거를 구분하여 보고한다.

네트워크관리사 2급의 IP 주소·서브넷·라우팅·기본 및 응용 프로토콜·네트워크 일반 학습에도 도움이 되는 구성을 지향한다. 그러나 자격증 전체 범위나 합격을 보장하는 과정은 아니다. Windows 서버 실기, 케이블 작업, 모든 통신 이론을 이 프로젝트가 대체한다고 설명하지 말라.

## 4. 기술 환경과 구현 원칙

개인 PC:
- Windows를 기본으로 한다.
- Wireshark, SSH·파일 전송 도구, 텍스트 편집기를 사용한다.
- 개인 PC는 서버 관리 접속과 캡처 분석에 사용한다.

공용 서버:
- Ubuntu Server 24.04 LTS를 기준으로 한다.
- 기존 PC의 Linux VM 또는 라즈베리파이 5를 사용할 수 있다.
- 장비의 CPU 아키텍처나 인터페이스 이름을 임의로 가정하지 않는다.
- Linux 네트워크 네임스페이스, veth, Linux bridge를 사용해 가상 장치를 구성한다.
- Docker·GNS3·Packet Tracer를 혼용하지 않는다.

실험 대상:
- IP·마스크·게이트웨이를 변경하는 대상은 가상 클라이언트다.
- 개인 Windows PC나 공용 서버 관리 인터페이스의 실제 네트워크 설정을 변경하지 않는다.
- 요청은 가상 클라이언트 내부에서 발생시키고, 해당 통신을 서버에서 캡처한다.
- 실험용 주소에 개인 PC 브라우저로 바로 접속할 수 있다고 가정하지 않는다.

패킷 수집:
- dumpcap 또는 tcpdump로 수집한다.
- 캡처 파일을 개인 PC로 내려받아 Wireshark로 분석한다.
- 파일 형식과 확장자를 일치시킨다.
- 캡처 위치, 실행 조건, 시작·종료 시각을 함께 기록한다.
- 캡처는 해당 트래픽이 발생하기 전에 시작한다.
- 설정·로그 조회도 함께 사용하며, 모든 원인을 패킷만으로 확정하려 하지 않는다.

## 5. 최종 네트워크 구조

환경은 다음 최종 구조를 향해 단계적으로 확장한다. 아래 전체 구성을 첫 주부터 만들지 않는다.

### 직원망

- 네트워크: 192.168.10.0/26
- 마스크: 255.255.255.192
- 브리지: pbl-br-staff
- 라우터 R1 직원망 측: 192.168.10.1/26
- DHCP 서비스: 192.168.10.2/26
- 초기 클라이언트:
  - pbl-c1: 192.168.10.10/26
  - pbl-c2: 192.168.10.11/26
- DHCP 도입 후 할당 범위: 192.168.10.30~192.168.10.50
- 기본 게이트웨이: 192.168.10.1
- DNS: 192.168.20.10

### 서버망

- 네트워크: 192.168.20.0/27
- 마스크: 255.255.255.224
- 브리지: pbl-br-server
- 라우터 R1 서버망 측: 192.168.20.1/27
- pbl-dns: 192.168.20.10/27
- pbl-web: 192.168.20.20/27
- 서버 기본 게이트웨이: 192.168.20.1
- HTTP 포트: TCP 8080
- HTTPS 비교 실습 포트: TCP 8443
- 내부 이름: web.lab.test → 192.168.20.20

### 정적 라우팅 실습용 확장

- 라우터 네임스페이스: pbl-r1, pbl-r2
- R1–R2 전송망: 192.168.30.0/30
- R1 전송망 측: 192.168.30.1/30
- R2 전송망 측: 192.168.30.2/30
- 원격망: 192.168.40.0/27
- R2 원격망 측: 192.168.40.1/27
- pbl-remote: 192.168.40.10/27
- 원격 호스트 기본 게이트웨이: 192.168.40.1

내부 NAT는 사용하지 않는다. 실습망 사이 통신은 지정된 가상 라우터를 거쳐야 하며, 호스트를 통한 우회 경로를 만들지 않는다. 라우터의 IP forwarding은 해당 라우터 네임스페이스 내부에서 설정한다.

위 주소가 실제 관리망이나 VPN과 충돌한다면 전체 계획을 일관되게 변경해야 한다. 일부 주소만 임의로 바꾸지 않는다.

## 6. 주차별 환경 발전 순서

1주차:
단일 LAN에 pbl-c1과 pbl-web을 구성한다. 웹 서버는 이때 192.168.10.20/26을 사용한다. 게이트웨이는 없다. 첫 요청·캡처·분석을 수행한다.

2주차:
pbl-c2를 추가하고 ARP·ICMP·MAC/IP·계층 구조를 분석한다.

3주차:
주소·서브넷 설계를 학습한다. 실제 환경은 단일 LAN을 유지한다.

4주차:
클라이언트 마스크를 통제된 조건에서 변경하여 로컬·원격 판단 차이를 확인한다.

5주차:
서버망과 R1을 추가한다. 웹 서버를 192.168.20.20/27로 이동하고 이전 주소를 제거한다. 기본 게이트웨이를 설정한다.

6주차:
라우터 양쪽에서 캡처하고 요청·응답과 반환 경로를 비교한다.

7주차:
R2와 원격망을 추가해 정적 경로와 반환 경로를 설정한다.

8주차:
직원망에 DHCP를 도입한다. 클라이언트의 기존 정적 주소를 제거하고 자동 할당을 검증한다.

9주차:
DNS를 구성하고 이름 조회부터 HTTP 응답까지 연결해 분석한다.

10주차:
웹 서비스 중단, HTTP 오류, 서버 응답 지연, HTTPS 관찰 범위를 비교한다.

11주차:
정답을 숨긴 단일 장애 사례를 분석하고 역할을 교대한다.

12주차:
교차 재현, 개인 평가, 결과 정리, 발표를 수행한다. 신규 기능은 추가하지 않는다.

이 순서는 공통 기준이며, 상세 가이드에서는 요청된 주차에 필요한 상태만 구성하라. 앞선 주차가 정상 완료되었다고 무조건 가정하지 말고 선행 상태 점검을 제공하라.

## 7. 공통 장애 시나리오

- 잘못된 서브넷 마스크.
- 잘못된 기본 게이트웨이 또는 기본 경로 누락.
- 정적 경로 또는 반환 경로 누락.
- 잘못된 DNS 설정.
- 웹 서비스 중단.
- 의도적으로 발생시킨 짧은 서버 응답 지연.
- 정상 통신과 구분하기 위한 HTTP 오류 응답.

처음에는 한 번에 하나의 원인만 변경한다. 복합 장애는 공통 과제를 완료한 사람의 선택 과제로만 사용한다.

장애 주입 시 어떤 설정을 변경했는지 기록하고, 정상 설정과 복구 명령을 준비한다. 실패가 실제로 재현되는지 운영자가 확인한 뒤 분석자에게 제공한다.

## 8. Wireshark의 역할

Wireshark는 프로젝트의 핵심 분석 도구다.

- ARP·ICMP·DHCP·DNS·TCP·HTTP 흐름 확인.
- Ethernet·IP·전송 계층 필드 구분.
- 연결과 요청·응답 추적.
- 서로 다른 캡처 지점 비교.
- 정상·장애·복구 상태 비교.
- 판단 근거가 되는 패킷 제시.

Wireshark가 주소나 라우팅을 설정하거나 장애를 자동 해결한다고 설명하지 말라.

초기에는 필요한 필터와 화면 조작을 제공하고, 후반에는 참여자가 목적에 맞는 필터와 증거를 직접 선택하게 한다.

다음과 같은 단정은 피한다.
- 재전송 표시가 있으면 공격이다.
- 패킷이 안 보이면 반드시 중간에서 유실됐다.
- ping 실패는 곧 서버 중단이다.
- TCP 연결 성공은 곧 웹 서비스 정상이다.
- DNS는 항상 UDP만 사용한다.
- 모든 DHCP 동작은 반드시 DORA 네 메시지로 나타난다.
- 하나의 HTTP 요청은 반드시 하나의 TCP 연결을 사용한다.
- HTTPS의 요청 경로·내용·상태 코드를 복호화 없이 항상 볼 수 있다.

## 9. 공통 실습 방법

모든 주차는 다음 흐름을 기본으로 한다.

1. 짧은 개념 학습.
2. 결과 예측.
3. 정상 상태 확인.
4. 캡처 시작.
5. 요청 또는 설정 변경 실행.
6. 캡처 종료·저장.
7. 개인 분석.
8. 팀 결과 비교.
9. 최소 수정과 정상 상태 복구.
10. 같은 요청으로 재검증.
11. 개인 기록 제출.

개인 기록에는 다음을 포함한다.
- 실험 목적.
- 실행 조건과 변경한 설정.
- 예상 결과.
- 관찰 사실.
- 캡처 파일과 근거 패킷 번호.
- 원인 후보와 판단 이유.
- 확인하지 못한 사항.
- 복구 방법과 재검증 결과.

실행 기록과 예상 결과를 구분하고, 실제로 실행하지 않은 결과를 측정값처럼 작성하지 않는다.

## 10. 운영·안전·재현 원칙

- 실습 자원에는 pbl- 접두사를 사용한다.
- 인터페이스 이름은 Linux 길이 제한을 만족하도록 짧게 작성한다.
- 호스트의 실제 NIC 주소, 기본 경로, 전체 방화벽을 변경하지 않는다.
- 전체 프로세스 일괄 종료나 시스템 전체 네트워크 초기화를 사용하지 않는다.
- 실습 프로세스의 PID·설정 파일·로그·임대 파일을 구분해 관리한다.
- DHCP는 격리된 실습망에서만 제공한다.
- 네트워크 네임스페이스는 파일시스템까지 자동 격리하지 않는다는 점을 고려한다.
- DHCP 클라이언트나 DNS 실습이 호스트 /etc/resolv.conf를 변경하지 않도록 한다.
- 캡처 파일의 크기와 보관 개수를 관리한다.
- 실습 계정과 가짜 데이터만 사용한다.
- 개인 PC와 서버 관리 접속을 실습 오류로 끊지 않는다.
- 설정 변경 실험은 공유 서버에서 동시에 겹쳐 실행하지 않는다.
- 각 실험 종료 후 정상 상태를 확인한다.

## 11. 가이드 작성 시 요구하는 설명 수준

뒤에 제공되는 주차 요청에 따라 상세 가이드를 작성할 때는 다음을 지켜라.

- “셋업 담당자 A의 활동”과 “실습 참여자 A·B·C·D의 활동”을 명확하게 구분한다.
- 명령마다 실행 위치를 표시한다. 예: 개인 Windows PowerShell, Linux 호스트, pbl-c1, pbl-r1, pbl-web.
- 관리자 권한이 필요한 작업을 표시한다.
- 작업 목적, 실행 방법, 예상 관찰, 의미, 실패 시 점검 순서를 제공한다.
- 스크립트가 필요하면 생략 없는 최소 동작 코드와 저장·실행·종료 방법을 제공한다.
- 재실행 시 자원 중복이나 기존 프로세스가 생길 수 있는 부분을 처리한다.
- 중요한 출력의 읽는 방법을 설명한다.
- Wireshark 필터와 확인할 필드·화면 조작을 구체적으로 제공한다.
- 실제 MAC 주소·관리 서버 주소·계정처럼 알 수 없는 값은 예시와 실제 입력을 구분하고 조회 방법을 설명한다.
- 이전 대화나 첨부되지 않은 자료를 읽었다고 가정하지 않는다.
- 명령을 외우는 것보다 “왜 이 확인을 하는가?”를 이해하도록 한다.
- 정답이나 교사용 해설은 실습자의 예측·분석 문제와 분리한다.
- 필요하면 공식 문서로 버전별 동작을 확인하고, 확인하지 못한 환경 차이는 명시한다.

## 12. 프로젝트 범위와 최종 평가

필수 범위:
IP 설계, 서브넷, 기본·정적 라우팅, 기본·응용 프로토콜, 패킷 분석, 설정 오류·서비스 장애 진단, 복구 검증.

필수로 추가하지 않을 것:
공격 도구 개발, 악성코드, 대규모 부하 공격, 머신러닝, 자동 차단, 실시간 대시보드, Kubernetes, 동적 라우팅, 복잡한 VLAN, 상용 보안 장비 연동.

최종 팀 결과물:
- 네트워크 구성도와 IP 설계표.
- 환경 실행·초기화 설명서.
- 정상·장애·복구 캡처.
- 실험 기록과 장애 진단 절차서.
- 평가용 사례와 별도 정답 해설.
- 최종 보고서와 시연 자료.

최종 개인 평가:
- 새로운 주소 조건의 서브넷 설계.
- 처음 보는 간단한 캡처의 흐름 설명.
- 단일 장애의 원인 후보와 근거 제시.
- 설정 수정 및 정상화 검증.

평가는 빠른 정답보다 정확한 관찰, 근거 있는 판단, 추가 확인의 적절성, 복구 검증을 중시한다. 네 명의 숙련도가 동일해지는 것을 보장하지는 않지만, 전원이 공통 핵심 활동을 직접 수행하고 최소 역량을 입증하도록 한다.
